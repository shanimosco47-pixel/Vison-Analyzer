**Status: diagnosis only. No production code was modified.**

or a generated artefact.

## 0. Blocking gap: there is no real test clip in this repository

Step 2 of Stage 0 asks for the test clip, the command that reproduces the
current result, and the source of the expected timing. **None of the three
exist here**, and I did not invent them:

| Needed | What is actually in the repo |
| --- | --- |
| Hand-held test clip | Nothing. The only videos are `tests/fixtures/{vfr_distributed,cfr_late_start,vfr_clustered_burst}.mp4`, generated by `scripts/make_vfr_fixtures.py` for frame-rate tests. They contain no cup. |
| Reproduce command | There is no analysis CLI. `python -m app.main` only starts the Flask server; analysis runs through the browser (upload → click outlet → analyse). |
| Expected/ground-truth timing | No labelled interval, no stopwatch reading, no operator notes anywhere in the repo or its history. |

`README.md` §7 quotes "Zahn cup, ground truth 17.50 s" — that is the
**synthetic** `zahn_video` fixture in `tests/conftest.py`, a static-camera
clip. It is not the reported hand-held recording.

So the real-footage acceptance criterion (**duration error within ±0.75 s on
labelled real hand-held clips**) is **not measurable today**, and I have not
pretended otherwise. See §7 for exactly what I need.

What I did instead, to avoid handing back nothing: I built controlled
hand-held clips whose ground truth is *drawn, not inferred*, reproduced the
reported symptom on them, and ran an ablation that isolates each candidate
cause. Ground truth is never taken from the detector's own output.

genuinely independent:

* **camera drift** — moves background, cup and stream together (hand-held phone)

## 3. Cause-by-cause evidence

### (a) The fixed ROI losing the outlet — **dominant cause**

The outlet drifts up to **33.4 px** (mean 16.2 px) from where it was clicked.
The ROI is 60 px wide, so the true outlet is **outside the analysis ROI in
15.8 % of frames** (`geometry.json`). Drift is mostly lateral; the outlet
never falls below the outlet band.

The decisive test (`ablate.py`) replaces the fixed ROI with an **oracle
tracker** — the guard crop is re-cut around the *ground-truth* outlet every
frame, and **nothing else in the pipeline changes**. That is the upper bound
on what a perfect Stage 1 tracker recovers:

| clip | fixed ROI | oracle-tracked ROI |
| --- | --- | --- |
| `handheld_white` | +2.37 s | **0.00 s** |
| `hand_only_white` | +1.87 s | **0.00 s** |
| `camera_only_white` | −4.20 s | **0.00 s** |
| `handheld_no_drops` | +0.03 s | **0.00 s** |
| `static_white` / `static_contrast` | 0.00 s | 0.00 s (no regression) |
| `handheld_contrast` | no detection | +5.13 s, end never confirmed |

**Tracking the outlet removes the entire timing error on every white-on-white
clip.** This is the fix.

### (b) …but "ROI coverage" and "stale background" cannot be cleanly separated

Re-cutting the ROI around the outlet does two things at once: the region
regains the outlet, **and** its contents stop moving, so the scorer's frozen
background model stays valid. I ran a separating experiment
(`widen_roi.py`): keep the ROI fixed but enlarge it to swallow the whole
drift envelope (60×216 → 140×256). If coverage alone were the cause, that
would fix it.

It makes things **worse**:

| clip | fixed 60×216 | fixed 140×256 |
| --- | --- | --- |
| `handheld_white` | +2.37 s | **+5.20 s** |
| `hand_only_white` | +1.87 s | **+6.00 s** |
| `handheld_no_drops` | +0.03 s | **+6.70 s** |
| `static_white` | 0.00 s | **detection fails entirely** |

So I am **not** allocating a number to "ROI coverage" versus "background
model staleness" — the experiment shows they are not additive and not
separable. What is established is the joint statement: *the region must both
contain the outlet and stop moving relative to its own background model*, and
only tracking delivers both. It also rules out the cheap fix: **do not just
make the ROI bigger.**

`StreamActivityScorer.score()` refreshes the background only while
`activity == 0.0` (`zahn_detector.py:229`). During 16 s of continuous stream
it is frozen solid while the cup drifts ~30 px away from it, so by the time
the drops end, the cup's nose and rim silhouette is a permanent difference
blob sitting in the top of the ROI. That is the phantom. Frames
`handheld_white__max_displacement__t021.700.png` and
`handheld_white__last_false_positive__t022.867.png` show it directly: the red
mask is a smear at the ROI top edge, with the true outlet (red cross) 27–32 px
outside the ROI.

A background model that refreshes on a fixed cadence instead is **not** the
answer either — the `tracked+bg` column in `ablation.json` dissolves the
stream into the reference image and collapses the measurement to 1.67 s
(−15.83 s error). The existing comment in the code is right about that.

### (c) Intermittent drops classified as continuous flow — **the mechanism that converts (a) into seconds**

`handheld_no_drops` is the control: identical motion, identical contrast, but
the liquid stops dead at 19.0 s instead of trailing into drops. Error
**+0.03 s**. Same clip *with* a drop tail: **+2.37 s**.

Why: the background stops being refreshed whenever `activity != 0`, so the
intermittent drop tail keeps the model frozen and stale right through the
period when it most needs to re-adapt. After the last real drop, 48 phantom
frames follow, and the **longest gap between consecutive phantoms is
0.167 s** — comfortably under `flow_end_persistence_s = 0.50 s`, so the
absence timer never accumulates and the clock keeps running until the
phantoms happen to thin out at 22.87 s.

Estimated contribution: essentially **all** of the +2.37 s overshoot on
`handheld_white` flows through this path — but it is a *consequence* of (a),
not an independent cause. Removing the tail removes the error; removing the
drift also removes the error.

### (d) Low-contrast reflections/shadows — **real, but not the driver here**

Contrast is *not* what separates real liquid from phantoms:

| | mean | min | max |
| --- | --- | --- | --- |
| real stream (3–19 s) | 14.12 | **10.29** | — |
| phantoms (20.5–22.87 s) | 12.21 | 11.71 | 12.98 |

**The distributions overlap.** Raising `min_abs_diff` to reject the phantoms
would also reject genuine weak-stream frames. Contrast alone cannot answer
the question, which is the argument for Stage 2 asking a *continuity*
question instead of a brightness one.

Also note the adaptive threshold is inert: `threshold > min_abs_diff` in
**0 of 703 frames**. Measured `noise_sigma` is 0.3–0.9, so
`noise_sigma_multiplier × sigma ≈ 3.2` never approaches the floor of 12. The
"threshold derived from the frame's own measured noise" is, in practice,
a fixed 12-grey-level threshold — because the MAD-of-residual estimator is
blind to coherent motion edges, which are sparse.

`handheld_contrast` is the one clip where contrast *is* a driver: even with a
perfect tracker it errs by +5.13 s and never confirms an end, because a
high-contrast cup silhouette against a moving background produces strong
tall-thin blobs. That is a genuine Stage 2 case — but it is **not** the
reported field condition, which is white-on-white.

### (e) Disturbance detection misfiring on camera motion — **contributes 0 s; it is inert, not misfiring**

| | measured | trigger |
| --- | --- | --- |
| `outside_changed_ratio`, max over the clip | **0.0147** | `disturbance_area_ratio = 0.35` (**23× away**) |
| frames flagged disturbed | **0 / 703** | — |
| `median_diff` | never reached | `disturbance_median_diff = 18.0` |

Every clip: `frames_disturbed = 0`. Smooth hand-held drift of a few px/frame
simply does not look like the scene-wide step change these thresholds were
written for. So it contributes **0 s** to the error, and the README's claim
that hand-held footage "will produce many disturbed frames and low
confidence" is **false** — the failure is silent and high-confidence instead.

Worth noting for Stage 3: even if it *did* fire, `FlowStateMachine.update()`
resets the absence timer on disturbed frames (`zahn_detector.py:391`), which
would push the reported end *later*. Making disturbance detection more
sensitive without changing that rule would make the reported bug worse.

### (f) The persistence/state-machine timer itself — **correct on its own; wrong inputs**

`PersistenceTimer` is time-anchored, not frame-counted, and both controls
(`static_white`, `static_contrast`) come back at **exactly 0.00 s** error.
The timer is not the bug.

It does have two properties that amplify bad input, and both are Stage 1
hazards to preserve against:

1. **Start requires an unbroken run.** `camera_only_white` starts **4.20 s
   late** even though the stream is plainly detected from 3.00 s — the outlet
   score flickers frame to frame (`0.542, 0.542, 0.062, 0.542, 0.000,
   0.542, 0.000 …`) because a drifting stream against a frozen background
   alternately clears and misses the fixed threshold. The longest unbroken
   run before 7.20 s is 13 frames; 9 are needed. A single bad frame restarts
   the whole 0.30 s.
2. **`end_s = _last_activity_s`.** The reported end is *whatever was last
   called liquid*. One phantom 2.4 s late moves the answer 2.4 s.

### (g) The gap case — falsely precise, exactly as feared

`handheld_gap_at_break` swings the outlet out of frame from 18.4 s to 21.2 s,
so the true break (19.0 s) **and** the true end (20.5 s) both happen while
nothing is observable. The detector reports **20.50 → 21.43 s,
`end_confirmed = True`, confidence 0.88** — a precise number for an interval
it never saw. Under the oracle tracker it reports 18.37 s, also
`end_confirmed = True`. Both are falsely precise; neither is flagged.

## 5. Proposed design

Deliberately smaller than the brief allows, because the evidence says the
error is one problem, not five.

### Stage 1 — outlet tracking (the whole fix for the reported symptom)

**Method: Shi–Tomasi features over the cup → pyramidal Lucas–Kanade with a
forward–backward check → `estimateAffinePartial2D` (RANSAC) → the outlet
carried as a rigid offset of that similarity transform.**

Justified by two measurements, not preference:

1. **CSRT and KCF do not exist in this build.** `requirements.txt` pins
   `opencv-python-headless` (not `-contrib`). Measured on 4.14.0:
   `TrackerCSRT_create` **absent**, `TrackerKCF_create` **absent**,
   `TrackerMOSSE_create` **absent**, `cv2.legacy` **absent**. Only
   `TrackerMIL` survives. `calcOpticalFlowPyrLK`, `goodFeaturesToTrack`,
   `estimateAffinePartial2D`, `findTransformECC` and `matchTemplate` are all
   present. Using CSRT would mean changing a pinned dependency for a
   capability the classical route already delivers.
2. **A single point on the outlet is too smooth to track, but the cup is
   not.** Measured min-eigenvalue (p95) on the white-on-white clip:

   | patch | std | mean grad | minEig p95 |
   | --- | --- | --- | --- |
   | clicked outlet, 32 px | 6.01 | 7.40 | 2.19 |
   | cup rim | 4.62 | 4.60 | 1.41 |
   | **cup handle** | 9.94 | **14.01** | **12.58** |
   | plain wall (control) | 1.11 | 1.27 | 0.66 |

   The handle carries ~6× the cornerness of the outlet. So track a *feature
   set over the cup region* (which the handle dominates) and derive the
   outlet from the fitted transform — exactly what the brief anticipated.

**Measured feasibility** (`track_probe.py`, error = Euclidean distance to the
drawn ground-truth outlet):

| clip | tracked | mean err | p95 | max |
| --- | --- | --- | --- | --- |
| `handheld_white` | 100 % | **1.01 px** | 1.73 px | 2.26 px |
| `hand_only_white` | 100 % | 0.82 px | 1.70 px | 1.97 px |
| `camera_only_white` | 100 % | 0.51 px | 0.88 px | 1.11 px |
| `handheld_contrast` | 100 % | 0.60 px | 0.98 px | 1.17 px |
| `handheld_gap_at_break` | 84.6 % | 5.71 px | 30.06 px | 30.99 px |

1 px mean = **1.7 % of ROI width**, **0.33 stream widths** — which is how I
propose to state the tracking-accuracy criterion, scale-relative as required.
Cost: 550 frames/s in the probe (which decodes full frames); production will
track inside a bounded search window, so the current 701 frames/s should land
around 400–500 frames/s. Still ~15× real time.

The `handheld_gap_at_break` row is the important one: the tracker *survives*
the outlet leaving frame and comes back **31 px wrong**, silently. So loss
detection is not optional, and reacquisition must be re-verified against the
reference patch — not assumed from the tracker still returning a number.

**Tracking states**

* `tracked` — RANSAC inliers ≥ threshold, forward–backward residual within
  tolerance, per-frame displacement within the configured bound. Valid for
  scoring and persistence.
* `predicted` — constant-velocity bridge across a gap shorter than
  `max_bridge_s`. **Diagnostic only.** Not used to confirm flow start or flow
  end, and not counted as liquid evidence. Nothing in my data justifies
  trusting it for timing.
* `lost` — everything else. Excluded from flow scoring entirely.

**Timestamps and persistence — the part that must not reintroduce the bug**

* Persistence timers stay anchored to original video timestamps.
  `PersistenceTimer` already does this correctly and I do not intend to
  touch its contract.
* `lost` frames are **excluded**, not treated as absence — but excluding them
  must not compress elapsed time, so the absence timer measures
  wall-clock span between *trusted* observations, and a `lost` run longer
  than `max_bridge_s` **invalidates the run in progress** rather than
  pausing and resuming.
* When flow-end is confirmed after a gap, report the **earliest supported
  transition timestamp** (last trusted activity), and carry an explicit
  uncertainty bound of `[last_trusted_activity, first_trusted_absence]`.
* If that bound exceeds `max_endpoint_uncertainty_s`, mark the endpoint
  **unconfirmed** and refuse to report a precise duration. `handheld_gap_at_break`
  becomes the regression test for this: today it returns 21.43 s "confirmed";
  it must return a bounded, unconfirmed interval.
* ROI and guard band are redefined **relative to the tracked position each
  frame**.

**Config** — four new keys only: `track_max_displacement_px`,
`track_min_inliers`, `max_bridge_s`, `max_endpoint_uncertainty_s`.

### Stage 2 — recommend **deferring the full build**

Stage 2 is gated on "only if Stage 0 shows contrast/tracing is a material
driver". On the reported condition (white-on-white, hand-held) it is **not**:
tracking alone takes the error to 0.00 s. Building continuity tracing now
would be complexity chasing a cause I measured as not-the-cause.

What I *do* propose from Stage 2, because §3(d) shows the current threshold
is untrustworthy at the margin:

* an explicit **`unknown`** frame classification when no confident local
  signal exists — never a silent fallback to the global threshold, since that
  threshold is exactly what produces the phantoms;
* `unknown` never counts as "flow present";
* isolated `unknown` frames → neither start nor stop persistence; short
  `unknown` runs → widen the endpoint uncertainty bound; prolonged `unknown`
  runs (> `max_endpoint_uncertainty_s`) → endpoint unconfirmed, confidence
  capped, measurement flagged.

The one clip that genuinely needs continuity tracing is `handheld_contrast`
(+5.13 s even with a perfect tracker). If you have high-contrast hand-held
footage in the field, say so and I will build Stage 2 properly. Otherwise I
would rather ship Stage 1 and re-measure.

### Stage 3 — partial, and honest about it

Global camera motion is a *different* problem from cup tracking, and §3(e)
shows the guard band currently contributes nothing. Proposal: estimate global
motion from background features **outside** the cup box, reusing the same
RANSAC fit, and expose `clear` / `disturbed` / **`unavailable`** — with
`unavailable` when inlier support is too low, never `clear`. It will handle
translation and mild rotation/scale; it will **not** handle motion blur,
rolling shutter, or exposure steps. And the "disturbed frames reset the
absence timer" rule in §3(e) must be revisited at the same time or Stage 3
will lengthen measurements.

### Confidence

`handheld_white` returning **0.98 confirmed** while 2.37 s wrong is the
headline defect. Confidence must fall for hand-held runs: tracked-frame
fraction, mean per-frame outlet displacement, and endpoint uncertainty all
become inputs, and any `lost`/`unknown` run beyond the configured duration
forces `review` regardless of the other terms.
